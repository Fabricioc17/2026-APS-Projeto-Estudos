# 4.2.2 Modelagem de Casos de Uso

## Atores

Dois papéis usam o StudyFlow. O ator é o papel, não a pessoa. Nas histórias da 4.2.1 o Diretor Veiga fala como diretor. No diagrama o ator é **Diretor**, como está em "Quem usa" da 4.1.

Quem opera o sistema é o ator, mesmo quando outra pessoa se beneficia. Na HU03 quem fala é o aluno, mas quem disponibiliza o conteúdo na plataforma é o diretor. Por isso a postagem de materiais é um caso de uso do diretor.

| Ator | Quem é | O que faz no sistema |
| :--- | :--- | :--- |
| **Aluno** | estudante com cadastro na escola | consulta os materiais de estudo do PSS e visualiza suas tarefas pendentes |
| **Diretor** | quem gerencia o reforço. Hoje, o Diretor Veiga | cadastra alunos e disciplinas, lança notas, publica cronogramas de reforço e envia materiais |

## Casos de uso

Cada caso de uso é um objetivo que um ator alcança no sistema. O nome é o mesmo do requisito que ele atende, letra por letra.

Nem todo requisito vira elipse. O RF06 (Sinalizar criticidade) é algo que o sistema faz de forma automática após o lançamento de uma nota, não um objetivo que alguém inicia diretamente. Ele aparece como passo da especificação, mais abaixo.

| Caso de uso | Ator | Atende |
| :--- | :--- | :--- |
| **Registrar aluno** | Diretor | RF01 |
| **Lançar notas** | Diretor | RF02 e RF06 (a sinalização automática é o passo 9 do fluxo principal) |
| **Publicar cronograma** | Diretor | RF03 |
| **Hospedar material** | Diretor | RF04 |
| **Listar tarefas** | Aluno | RF05 |
| **Gerenciar disciplinas** | Diretor | RF07 |

## Especificação do caso de uso principal

Lançar notas é o caso de uso que o sistema existe para fazer: é ele que tira o controle dos alunos em risco das planilhas soltas. Por isso é o especificado.

| Campo | Descrição |
| :--- | :--- |
| **Caso de uso** | Lançar notas |
| **Ator** | Diretor |
| **Pré-condição** | O aluno e a disciplina estão cadastrados (RF01 e RF07), e o diretor está identificado no sistema (RNF02). |
| **Pós-condição** | A nota de recuperação está registrada, e o status de criticidade do estudante é atualizado no painel (RF06). |

##### Fluxo principal
1. O diretor solicita o lançamento de uma nota de recuperação.
2. O sistema mostra os alunos cadastrados e confirma que a turma está vinculada.
3. O diretor seleciona o aluno desejado.
4. O sistema apresenta as disciplinas cadastradas.
5. O diretor seleciona a disciplina correspondente.
6. O sistema solicita o valor da nota de recuperação.
7. O diretor informa a nota.
8. O sistema registra a nota vinculada ao aluno e à disciplina.
9. O sistema verifica a quantidade de notas vermelhas do aluno automaticamente (RF06).
10. O sistema atualiza a condição de criticidade do aluno e confirma o sucesso da operação.

##### Fluxo alternativo
* **A1, no passo 8:** Já existe uma nota registrada para o aluno e a disciplina. O diretor solicita a atualização da nota, o sistema substitui o valor anterior pelo novo, reavalia a criticidade (RF06) e confirma a alteração.

##### Fluxos de exceção
* **E1, no passo 2:** O aluno não está cadastrado. O sistema informa que o registro não foi localizado e interrompe o lançamento. O caso de uso termina sem a pós-condição.
* **E2, no passo 4:** A disciplina não está cadastrada. O sistema avisa que a matéria não foi encontrada e bloqueia a operação. O caso de uso termina sem a pós-condição.

A diferença entre A1 e E1 está no fim. No fluxo alternativo, o lançamento acontece por outro caminho (atualização). Na exceção, ele não acontece.

## Rastreabilidade com a 4.2.1

| Requisito | Caso de uso | Onde aparece |
| :--- | :--- | :--- |
| **RF01** Registrar aluno | Registrar aluno | elipse, e pré-condição de Lançar notas |
| **RF02** Lançar notas | Lançar notas | elipse, e especificação completa |
| **RF03** Publicar cronograma | Publicar cronograma | elipse |
| **RF04** Hospedar material | Hospedar material | elipse |
| **RF05** Listar tarefas | Listar tarefas | elipse |
| **RF06** Sinalizar criticidade | nenhuma elipse | passos 9 e 10 do fluxo principal de Lançar notas |
| **RF07** Gerenciar disciplinas | Gerenciar disciplinas | elipse, e pré-condição de Lançar notas |

**Todo requisito tem lugar.** Seis viraram elipse com o mesmo nome. O RF06 não virou por ser um comportamento automático, e a tabela diz onde ele mora.

**Toda elipse tem requisito.** Nenhum caso de uso apareceu sem um requisito por trás. Se aparecesse, seria sinal de requisito faltando na 4.2.1, e o conserto seria lá. 

**O que a especificação mudou.** Escrever o fluxo mostrou uma regra que a 4.2.1 não tinha: qual valor de corte define uma nota como vermelha. Ela ficou anotada como pendência na modelagem para a próxima conversa com o Diretor Veiga.
